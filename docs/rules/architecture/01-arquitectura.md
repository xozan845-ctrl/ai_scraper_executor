# 01 — Reglas Doradas de Arquitectura

Aplica a: el reparto entre capas (vista histórica de runtime; el modelo **canónico**
es hexagonal y vive en [`03-arquitectura-hexagonal.md`](./03-arquitectura-hexagonal.md),
`R-HX-1`), la comunicación entre `api` y `worker`, el orden de compilación del monorepo
y el comportamiento cuando una dependencia no está disponible.

## Reglas

| ID | Regla |
|---|---|
| R-AR-1 | **La IA es el cerebro, el motor es el motor**: ninguna función de este repo llama a un modelo de lenguaje para decidir *cómo* se ejecuta algo. El LLM decide **qué** se hace y lo expresa **exclusivamente** como comandos del DSL de [`../ai/01-dsl.md`](../ai/01-dsl.md) (`R-AI-1`). La ejecución, los reintentos, los presupuestos, el parseo y la persistencia los decide el código, nunca el modelo. Prohibido ejecutar `eval`, `Function`, un selector fuera del DSL o un comando inventado emitido por el modelo (`R-AI-4`). |
| R-AR-2 | **Una sola dirección de dependencia entre capas, y `apps/*` es quien compone**: la vista histórica de runtime era `INTERFACE` (`apps/api`) → `ORCHESTRATION` (`libs/infrastructure/queue`, `libs/infrastructure/storage`) → `INTELLIGENCE` (`packages/ai`, `libs/infrastructure/ai-providers`) → `EXECUTION` (`libs/domain/ai`, `libs/infrastructure/execution`, `libs/infrastructure/crawler`) → `DATA` (`libs/infrastructure/storage`, `libs/infrastructure/mongodb`, `libs/infrastructure/redis`). **El modelo canónico de capas es el hexagonal** (`R-HX-1`): esta lista sobrevive solo como mapa de runtime. Invariante que no cambia: una lib solo importa de libs, nunca de `apps/*`; `apps/*` es quien compone. Prohibido que `packages/*` o `libs/*` importe de `apps/*`: rompe `npm run build:core` y el orden de resolución de `tsconfig.base.json`. |
| R-AR-3 | **Un solo sentido entre API y worker, y con cola**: la API **nunca** ejecuta un job. `POST /api/v1/jobs` valida, persiste y encola; el consumo ocurre **solo** en `apps/worker` (BullMQ). El estado del job viaja por la cola y por la base de datos, nunca por una llamada HTTP interna ni por un fichero. El escalado horizontal (`docker compose up --scale worker=N`) debe funcionar sin tocar la API; por eso toda métrica lleva el label `instance` (`R-TM-3`). |
| R-AR-4 | **Orden de build explícito y `paths` a `dist/`**: `npm run build:core` compila los packages en orden de dependencia (`core` y `security` primero), y `tsconfig.base.json` mapea `@ai-scraper/*` a `packages/*/dist`, **nunca a `src`**. Cada package tiene su `tsconfig.json` con `rootDir: src` y `outDir: dist`. No se añade un package a `build:core` sin añadirlo antes a esa cadena ni sin declarar su lugar en ella. |
| R-AR-5 | **Nada de artefactos compilados dentro de `src/`**: ejecutar `tsc` sin `-p packages/<x>/tsconfig.json` emite `.js`, `.d.ts` y `.map` junto al `.ts` y rompe el lint, porque el lint ignora `**/dist/**` pero **no** `src/*.js`. Si aparecen, se borran y se reconstruye con `npm run build -w <package>`. Prohibido versionar cualquier `.js`, `.d.ts` o `.map` bajo `apps/*/src/` o `packages/*/src/`. |
| R-AR-6 | **Todo store tiene fallback en memoria y avisa por log**: Postgres, Mongo y Redis tienen implementación en memoria (`InMemoryJobStore`, `InMemoryJobQueue`, caché/rate-limit/métricas en memoria) para arrancar sin Docker. Al caer al fallback se emite un `warn` con el motivo. **Nunca se falla en silencio** (prohibido un `catch` vacío que trague el error sin registrarlo). El fallback **nunca** es el camino de producción: si `DATABASE_URL`, `MONGODB_URI` o `REDIS_URL` apuntan a algo inalcanzable en producción, eso es un incidente, no un modo de operación → `R-DI-6`. |
| R-AR-7 | **Toda integración con un tercero va detrás de un adaptador**: el LLM entra por `libs/infrastructure/ai-providers` (`provider.factory.ts` elige `OpenRouterProvider`, `CustomEndpointProvider` o `FallbackAIProvider`); el acceso HTTP a terceros entra por `libs/shared/security` (`safeFetchText`) y `libs/infrastructure/crawler`. Ninguna otra capa importa el SDK de OpenRouter/Ollama ni hace `fetch` a un sitio externo directamente. Motivo: aislar el dominio y poder testear con dobles sin red (`R-QA-2`) → `R-AI-8`. |
| R-AR-8 | **Cola de muertos y reintentos con espera creciente**: el consumo de la cola registra reintentos y, al agotarlos, el job va a la cola de muertos `scraping-jobs-dead` (`SCRAPING_DEAD_QUEUE`) en lugar de reintentar indefinidamente. Un job en la cola de muertos es un estado a investigar, no un error silencioso, y su métrica no dispara alerta por existir sino por crecer (`R-TM-5`). Un reintento explícito desde la API limpia los artefactos previos del job (`clearJobArtifacts`) antes de volver a encolarlo, para no duplicar resultados ya persistidos. |
| R-AR-9 | **Cambiar el esquema de datos, el contrato público de la API o el orden de build es un cambio normativo**: una migración de Prisma, un campo nuevo en un DTO público o tocar `build:core` pasan por el flujo de PR (`R-PR-*`) y, si cambian el comportamiento esperado, exigen añadir o ajustar el test que lo fija (`R0`). Un cambio de esquema nunca se aplica a mano en un entorno compartido: se escribe la migración y se aplica con `prisma migrate deploy` (`R-DB-6`). |
