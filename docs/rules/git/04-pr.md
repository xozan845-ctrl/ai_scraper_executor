# 04 — PR: rama, cuerpo, checks y merge

Cierra el flujo de git: [`01-stage.md`](./01-stage.md) → [`02-commits.md`](./02-commits.md) →
[`03-push.md`](./03-push.md) → **este**. Hasta aquí las reglas describían cómo se sube
trabajo a `origin`; ninguna decía **por dónde** entra ni **cuándo** se considera
terminado. Este archivo cierra ese hueco: `main` se alimenta **solo** por merge de PR
verificado.

## Reglas

| ID | Regla |
|---|---|
| R-PR-1 | **Rama por trabajo, salida desde `main`**: prohibido commitear directo a `main` (R-GE-4). Cada cambio vive en una rama `tipo/ámbito-descripción` (`fix/ssrf-subrecursos`, `test/limites-extremos`, `docs/reglas-ai`) creada desde `main` actualizado: `git fetch origin && git pull --rebase origin main && git switch -c <rama>`. Los ámbitos son los de este repo (`api`, `worker`, `security`, `engine`, `limits`, `metrics`, `redis`, `ai`, `auth`, `crawler`, `persistence`, `client`, `scripts`, `rules`, `ci`, `docs`). No hay saltos entre entornos que promover: `main` es el destino (R-GE-1, R-GE-5). Excepción: un incidente en producción se corrige con una rama `hotfix/...` desde `main` y su PR a `main` (R-GE-6), que es la excepción y no el método. |
| R-PR-2 | **Un PR = una unidad revisable**: un tema, una capa, una decisión — el mismo criterio de unidad temática que R-GC-3 pero a escala de PR. Si el cuerpo dice "y además", el PR se parte en dos: si el segundo depende del primero, se apila (`gh pr create --base <rama-1>`); si es independiente, se abre en paralelo. Nunca un PR que mezcle refactor con feature ni con formato. |
| R-PR-3 | **Verificación antes de abrir**: R-GC-5 en verde para el ámbito tocado, y `npm run build` cuando el cambio cruza áreas. Un PR abierto con verificación en rojo solo se admite para pedir opinión y se marca explícitamente en el título (`[WIP]`); en ese estado no se mergea (R-PR-6). |
| R-PR-4 | **El cuerpo del PR es la evidencia**: pegar el [`CHECKLIST`](../_meta/CHECKLIST.md) marcado y una tabla de las verificaciones **efectivamente ejecutadas** con el comando real y su resultado (no "los tests pasan"): en la base del PR, `npm run build`, `npm run lint` y `MONGODB_MOCK=1 npm test` con su recuento de tests; si el cambio toca la capa de red, la salida del comando manual que la cubra. Si una capa de la matriz de [`06-estandares-cobertura.md`](../test/06-estandares-cobertura.md) no aplica, se dice por qué. Un PR sin evidencia de ejecución no se revisa. |
| R-PR-5 | **Commits trazables**: los commits del PR cumplen R-GC-1..R-GC-4 (Conventional Commits en español, un tema cada uno, ID de regla citado). Con más de 3 commits, el cuerpo del PR declara en qué commit vive cada parte, para que un revisor pueda leerlos en orden. |
| R-PR-6 | **Checks verdes en la cabeza del PR antes de mergear**: el job `build-test-lint` (R-CI-1) debe estar en `success` **en el SHA de la cabeza del PR** (`gh pr checks <n>`). El verde de un run anterior no prueba nada sobre el actual — mismo criterio que R-GP-6 y R-CI-6. Run en rojo ⇒ fix-forward con commit nuevo (R-GP-3); nunca se mergea hoping. Recordar qué es y qué no es un check: hoy ese job cubre build, lint, suite unitaria, **cobertura** y **la puerta de seguridad** (`G-1`, `G-3`, `G-7`, `R-QA-6`); la integración, el contrato y el E2E **no** son checks todavía (`G-4`, `G-5`, `G-6`). |
| R-PR-7 | **Estrategia de merge: `--rebase`**. El historial de `main` es estrictamente lineal; prohibido `--squash` (aplana la unidad temática y destruye los mensajes con ID de regla, que son la documentación viva del porqué — R-GC-3/R-GC-4) y prohibido el merge commit. R-GP-5 ya prohíbe el merge de sincronización: esto prohíbe además el merge de integración. |
| R-PR-8 | **`main` se verifica después del merge**: al mergear, el trabajo no está terminado hasta ver `completed success` en el run de `ci.yml` del **nuevo** SHA de `main`, no en el del PR. `main` en rojo es un incidente: se diagnostica con `gh run view <id> --log-failed` (R-CI-6) y se corrige con commit nuevo o rollback (R-CD-12); no se "deja corriendo". Un PR que toque una capa sin job (integración, contrato, E2E, auditoría) no se da por cerrado solo porque `ci.yml` pasó: quien lo mergea ejecuta la comprobación manual correspondiente y la deja escrita en el PR. |
| R-PR-9 | **Cierre**: tras el merge, rama eliminada (`git push origin --delete <rama>`, local con `git branch -d`) y PR marcado como tal. Prohibido dejar una rama publicada sin PR abierto, y prohibido un PR abierto que ya no se va a mergear sin `gh pr close` con la razón. |

## Verificación

```bash
# main sigue lineal (R-PR-7): debe imprimir 0
git rev-list --merges --count origin/main

# la rama publication == la rama de trabajo (R-PR-1)
git log origin/main..HEAD --oneline

# checks verdes en la CABEZA del PR (R-PR-6), no en un run viejo
gh pr checks <n>
gh pr view <n> --json headRefOid,headRefName,mergeable

# main verificado tras el merge (R-PR-8): el run debe ser del SHA nuevo
gh run list --branch main --limit 3 --json headSha,conclusion,status
```
